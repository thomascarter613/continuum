## Step 1 — Establish the System Charter

I’m going to make a few initial decisions rather than asking you to design everything from scratch. You can challenge any of them later, but **I’ll carry the design burden unless there is a genuine product-level decision that requires your judgment.**

### Working project name

For now:

# **Continuum**

The name is provisional. The idea is that the project maintains continuity of understanding across humans, AI agents, sessions, and time.

We won't spend time branding yet.

---

# 1. System Thesis

The central thesis is:

> **A software project should possess a persistent, machine-readable model of its own intent, knowledge, decisions, constraints, state, history, and relationships, independent of any particular human or AI session.**

AI agents then become **participants in the project**, rather than the place where project knowledge lives.

This gives us:

```text
                    PROJECT
                       │
        ┌──────────────┴──────────────┐
        │                             │
        ▼                             ▼
 Persistent Project              Source Code
    Knowledge                     & Tests
        │                             │
        └──────────────┬──────────────┘
                       │
                       ▼
                 CONTEXT ENGINE
                       │
                       ▼
                 AI / HUMAN
                 PARTICIPANTS
```

The project is persistent.

The participants are replaceable.

---

# 2. Problem Statement

AI-assisted software development has an architectural weakness:

**the development process is conversational, but the project is persistent.**

Important information becomes distributed across:

* AI conversations
* source code
* commits
* issues
* documents
* tickets
* notes
* human memory
* design discussions
* abandoned approaches
* assumptions
* AI-generated plans
* decisions that were never formally recorded

Consequently, an AI agent entering a project often cannot reliably distinguish:

```text
What was decided?
What was merely suggested?
What is still uncertain?
What is obsolete?
What is actually implemented?
Why was something implemented this way?
What constraints must not be violated?
What does the human actually want?
```

Continuum exists to solve that problem.

---

# 3. The Fundamental Separation

This is perhaps the most important architectural principle.

We will explicitly separate:

### Project Memory

Persistent knowledge about the project.

### Project State

What is currently true about the project.

### Project Evidence

Observable facts supporting those claims.

### Project Context

The subset of knowledge necessary for a particular task.

### Session

A temporary interaction between a participant and the project.

### Participant

A human, AI agent, tool, or external system interacting with the project.

Therefore:

```text
Memory ≠ Context ≠ Session ≠ Agent
```

This distinction will permeate the entire architecture.

---

# 4. Project Memory Is Not Documentation

This is a critical distinction.

Traditional documentation is primarily intended for **human consumption**.

Continuum's project memory is intended to be:

> **machine-readable institutional knowledge.**

It must therefore support things ordinary documentation does poorly:

* structured relationships
* provenance
* versioning
* temporal validity
* confidence
* authority
* supersession
* contradiction
* dependency
* traceability
* machine retrieval
* context assembly

Markdown may still be used for human-readable representations.

But Markdown itself isn't the model.

---

# 5. Project Truth

Continuum needs an explicit concept of **truth**.

Not philosophical absolute truth.

Rather:

> **What does the project currently recognize as authoritative knowledge?**

We will distinguish at minimum:

```text
OBSERVED
DERIVED
PROPOSED
ASSUMED
DECIDED
REJECTED
SUPERSEDED
UNKNOWN
CONFLICTED
```

For example:

```text
"PostgreSQL is used by the application."

SOURCE:
repository configuration

STATUS:
OBSERVED
```

Whereas:

```text
"We should use PostgreSQL."

SOURCE:
AI conversation

STATUS:
PROPOSED
```

And:

```text
"Use SQLite for local persistence."

SOURCE:
ADR-017

STATUS:
DECIDED
AUTHORITY:
human
```

The AI must not silently promote:

```text
PROPOSED → DECIDED
```

That distinction will become extremely important.

---

# 6. Authority

Continuum will have an explicit **authority model**.

Tentatively:

```text
Human authority
      │
      ▼
Accepted project decisions
      │
      ▼
Verified project evidence
      │
      ▼
Derived knowledge
      │
      ▼
AI proposals / hypotheses
```

An AI can:

* observe
* analyze
* infer
* propose
* implement within authorization
* identify contradictions
* request decisions
* record evidence

But an AI should not silently redefine project intent.

This gives us a fundamental rule:

> **AI may reason about project truth; it does not unilaterally determine project truth.**

---

# 7. Memory Must Be Temporal

Another principle I'm establishing now:

**Nothing important should be treated as timeless if it can change.**

Consider:

```text
Use React
```

That may have been true in 2025.

Perhaps in 2027 the project moves to SolidJS.

We don't want to erase history.

We want:

```text
Decision D-001
  valid: 2025-01 → 2027-03
  decision: React

Decision D-104
  supersedes: D-001
  valid: 2027-03 → present
  decision: SolidJS
```

Thus project memory becomes a **history of evolving understanding**, rather than a constantly rewritten wiki.

---

# 8. Context Is Generated

This is another foundational decision.

We will **not** assume:

```text
All project memory → AI context
```

Instead:

```text
                     PROJECT MEMORY
                           │
                           ▼
                    CONTEXT ENGINE
                           │
              ┌────────────┼────────────┐
              │            │            │
           Task          State       Authority
              │            │            │
              └────────────┼────────────┘
                           ▼
                  RELEVANCE ANALYSIS
                           │
                           ▼
                    CONTEXT PACKAGE
                           │
                           ▼
                           AI
```

A context package should answer:

> **What does this participant need to know to perform this particular operation safely?**

That means context is **task-specific, dynamic, and disposable**.

---

# 9. Context Must Be Explainable

This is an important requirement I'll add.

If Continuum produces:

```text
CONTEXT-042
```

the system should be able to explain:

```text
Included:
REQ-017
because task affects authentication.

ADR-009
because it governs authentication architecture.

CON-004
because it constrains identity providers.

SRC-122
because it implements the affected component.

TEST-031
because it verifies the relevant behavior.
```

The AI shouldn't receive a mysterious blob of retrieved information.

We need **context provenance**.

Eventually this allows:

```text
Why did you tell me this?
Why did you omit that?
Why is this decision relevant?
What project rule caused this constraint to appear?
```

---

# 10. Contradictions Are First-Class

Continuum must assume contradictions will happen.

For example:

```text
ADR-004:
Use SQLite.

config/database.ts:
PostgreSQL connection.

README:
The system uses SQLite.
```

We should not immediately "fix" this.

Instead:

```text
CONFLICT-021

Subjects:
ADR-004
database.ts
README.md

Conflict:
Persistence technology disagreement.

Status:
UNRESOLVED

Impact:
HIGH
```

Then an AI can say:

> "I found a contradiction in the project memory and implementation. I need to resolve this before modifying persistence."

That's much safer than confidently proceeding.

---

# 11. The System Must Be Repository-Native

For the initial version, I'm choosing:

> **Local-first, repository-native, Git-friendly.**

The project should be usable without a cloud account.

A developer should be able to:

```bash
git clone project
```

and possess the project's institutional memory.

That means:

```text
Git repository
│
├── source
├── tests
├── configuration
└── project memory
```

The project's memory should travel with the project.

Cloud synchronization can come later.

---

# 12. Human Readability Is Mandatory

Machine-readable doesn't mean machine-only.

Every important concept should have:

1. canonical structured representation
2. human-readable representation
3. machine-readable relationships
4. provenance

A developer should be able to open the repository in a text editor and understand what is happening.

No proprietary database should be required to understand the project.

---

# 13. AI Independence

Continuum will not be built around OpenAI, Anthropic, Google, GitHub Copilot, or any other particular AI.

Instead:

```text
                  CONTINUUM
                      │
                 Context API
                      │
        ┌─────────────┼─────────────┐
        │             │             │
       GPT          Claude        Gemini
        │             │             │
      Codex          CLI           API
        │             │             │
        └─────────────┼─────────────┘
                      │
                 Same Project
```

The project's memory remains independent of the model provider.

# 14. AI Sessions Become Disposable

This is one of our most important success criteria.

Suppose:

```text
Monday:
GPT session
```

Then:

```text
Tuesday:
Claude session
```

Then:

```text
Wednesday:
Codex
```

Then:

```text
Thursday:
local model
```

None of that should matter.

Any sufficiently capable participant should be able to reconstruct the relevant project state.

Therefore:

> **Continuity must survive the death of the conversation.**

That's essentially the product's raison d'être.

* an AI coding agent

It may integrate with many of these.

But its fundamental responsibility is:

> **Maintain and operationalize persistent project understanding.**
